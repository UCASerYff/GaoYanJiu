# 研究资料交接与人工验收

本文说明 GaoAction V1 的产品流程及验收边界。隔离测试、能力表兼容和打开请求成功，都不表示实际应用之间的编辑或 OCR 业务已经完成。

## 已安装提供方与缺失提供方

研究端按明确的 bundle ID 查找应用，核对应用资源内的 `GaoCapabilities.json`、实际版本、动作和参数 schema，再显式指定该应用打开交接包。能力不符或提供方未安装时，发送功能不可执行；私有请求包和本地 session 保留，可导出或在 Finder 显示。不自动安装提供方，不把缺失提供方标为完成。

- `documents.open`：`com.gaoseries.GaoWenJian`。
- `ocr.files`：`com.gaoseries.GaoJieTu`。
- `files.choose`：`com.gaoseries.GaoZhengLi`；须以实际安装和能力表为准。

请求包有效期为 120 秒。过期后不能绕过校验直接发送旧包。用户可以从当前研究条目明确重新发起，并重新核对当前原件与目标。曾经打开的请求可能仍在提供方执行，不能因关闭窗口、退出应用或没有收到结果就推断失败并自动重复操作。

## V4.06 入站文档导入与业务回执

`research.importDocuments` 接受经过校验的文件副本。V4.06 的能力表只接受空参数；本端由本人明确选择现有资料文件夹。旧请求中的非空 `targetRecordID` 会明确阻断，不把它静默解释为文件夹或自动选择第一个目标。

接收与关闭审核页都不表示导入完成，也不表示取消。只有本人“拒绝并取消”才持久记录 `cancelled`；本人确认后，记录目标与原始请求摘要，事务及全文索引全部完成才持久记录 `completed`。资料已经提交而索引尚未恢复时保持 `pending`，不能向调用方报告终态失败或取消。“交接回执…”中的“恢复未完成导入”可继续既有批准事务和索引，再恢复缺失回执；重发回执不重新导入。未批准的 pending 请求可从历史页明确取消；关闭页面不会自动取消，原请求过期时需由发送方发起新请求。

“发送回执给原发送方”或“导出回执”每次生成当前有效的新信封：`kind=result`，沿用原 `action`、`inReplyTo` 和相反的来源/目标，`parameters={}`、`items=[]`、`references=[]`，无错误时省略 `errorCode`。`provenance` 包含：

- `requestManifestSHA256`：最初校验到的原请求 `manifest.json` 字节摘要；不使用重新编码的摘要。
- `workflowState`：完成为 `imported`，其余与真实状态同名。
- `sources`：逐输入精确对应 `sourceItemID`、`sourceSHA256` 和状态；完成时全部为 `imported`，取消时均未导入。
- `saved`、本次计数和业务 `receiptID`；不含本机私有路径、原附件内容或其他库记录。

相同请求编号绑定同一请求摘要与经本人确认的目标。内容或目标改变会明确冲突，需由发送方重新发起。打开回执只表示交给目标应用处理，是否收到、如何显示由调用方独立核对；发送失败保留业务状态，可重试或从“交接回执…”重新发送。

## 文档编辑

1. 在研究资料条目选择外部编辑。研究端发送普通文档副本，保留原附件，记录原 ID、摘要、版本及请求 session。
2. 在提供方本人确认接收并实际编辑。`documents.open` 回执仅说明打开、部分打开、等待、取消或失败；回执不含编辑附件，`opened` 不是保存成功。
3. 使用提供方的“导出编辑副本”或等价的保留原格式导出功能，选择新的文件位置。导出文件并不表示已经导回研究库。
4. 回研究端原条目选择“导入编辑新版本…”，本人选择导出的文件，明确选择新版本或新附件。研究端核对原记录和版本摘要，先保留私有快照，再经事务 journal 提交和索引。
5. 检查新版本使用同一研究文档 ID，新附件使用独立 ID 且关联原件；原附件、历史记录和恢复快照保留。重复导入同一已提交操作不能再建记录。

提供方无需把编辑附件塞进 `documents.open` 结果。这会违背 V1 的打开回执语义；跨应用自动替换原附件也不受支持。

## OCR

1. 从明确选中的研究 PDF 或图像发起 OCR，发送副本，申请文字、JSON 和可搜索 PDF。未选择的资料不会随请求发送。
2. 在提供方本人确认范围与识别参数，检查逐页成功、失败及取消状态。使用提供方的“发送结果”交回研究端。
3. 研究端在全局审核页显示原件映射、输出、页号、逐页状态、可用页文字和缺失的来源信息；`pending`、`failed`、`cancelled`、`unsupported` 不应用，`partial` 和资料不完整的结果需明确审核。
4. 批准后，文字、JSON、PDF 作为受管派生附件保存，绑定输入 ID 和原 SHA256，原附件保留。JSON 中的真实逐页文字用于页来源；不从整段 TXT 猜页，不填造缺失的置信度或识别语种。
5. 提供方可以在发送时刷新结果 TTL 并生成新结果 UUID。只要原请求、动作、目标、验证内容及逐页来源相同，研究端复用同一业务 job；每个新信封仍有独立接收和业务回执，不重复建派生附件。

若研究端退出后需要重新审核，可在提供方对已保留产物再次选择“发送结果”，生成当前有效信封，不必重新执行 OCR。不要以历史时钟绕过过期请求检查。

V4.03 及更早版本的 journal 以原结果信封 UUID 命名，未保存完整原始意图。精确原 UUID 的恢复继续使用原 journal 和版本核对；换新 UUID 时，单凭已存页文字或状态无法证明完整来源一致，研究端会明确阻断并保留待复核，不自动关联旧 job 或创建重复附件。请先核对已导入附件；需要新的业务操作时，从原研究条目明确发起新请求。

## 文件选择

提供方只返回用户实际选择的引用或副本。引用不会授予权限；研究端独立核对身份、摘要与读取权限，必要时在本端重新选择。目标采用发起时记录的资料文件夹；目标缺失或旧 session 未记录目标时，必须明确重选，不能默认使用第一个文件夹。

引用本身可能不含摘要。研究端先安全读取并复制本次本人选择，再把实际 SHA256、字节数与扩展名绑定业务 job。同一引用在新信封中经本人重新选择了不同内容时，不能回放以前的选择；相同已验证内容才复用对应 job。

提交 journal 之前，研究端持久记录信封摘要与唯一业务 job 的待执行关联。它不等于已导入。中断后同一信封优先恢复原 job 与私有副本；若关联已写入而 job 尚未落盘，只有重新核实的内容和目标仍构成原意图时才可创建原 job，内容变化会明确冲突，不能重新绑定。

## 非 GUI 接线

- `recentSessions(limit:)` 和 `loadSession(_:)` 可读取待办。`prepared`、`opened`、收到回执及审核中的状态，都不等于业务完成。
- `receiveExchangeResultForReview(at:)` 只生成审核模型。
- `applyExchangeResult(_:userApproved:targetFolderID:reselectedReferences:)` 是审核页和隔离产品测试共用的业务入口。仅 journal 完整提交并完成索引后才写业务 receipt。
- `receiveResult(...).duplicate` 仅表示同一信封曾收到；`businessApplied` 和持久业务 journal 决定是否已经导入。不能用 transport duplicate 阻止尚未批准或中断后的恢复。

## 需要本人执行的实际验收

默认不运行冒烟。已明确授权的定向实际验收须使用公开合成样本并取得共享前台租约；需要本人认证、实体操作或长期条件时另行确认。实际验收分别记录：双方实际安装版本与能力；研究端发起和提供方接收；实际编辑、导出、本人导回；实际 OCR 后本人审核；多输出关联原件与页号；partial 不伪装全部完成；重复发送不增加附件；原附件和业务数据保留。

未执行这些操作时，应报告“实际双方 GUI 流程未验收”。测试临时资料、假能力表、协议编解码与生产适配器回归，只证明其各自覆盖的代码路径。
